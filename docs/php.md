## php-8.5 workflow

```
rpmbuild-php-8.5  (базовая фаза: RPM + aursu/php85build:<os>-build)
        │  notify → createDispatchEvent(php85-base-ready)
        ▼
rpmbuild-pipeline-php :: «PHP 8.5 pipeline»   ← этот файл
        │  uses → rebuild-php.yml (php=8.5)
        ▼
rebuild-php.yml  :: DAG из ~9 джоб
        │  каждая джоба → dispatch-and-wait.yml (mint token + gh workflow run + ждать)
        ▼
rpmbuild-php-<ext> repos  и в конце  rpmbuild-php-8.5 :: images.yaml
```

Три уровня переиспользуемых workflow: `pipeline` → `rebuild-php` → `dispatch-and-wait`. GitHub разрешает вложенность до четырёх уровней, так что запас ещё есть, но небольшой.

## «PHP 8.5 pipeline» — по директивам

`name: PHP 8.5 pipeline` — отображаемое имя в UI.

`on:` — два триггера:

- `workflow_dispatch` с входом `ref` (`description` — подсказка в UI, `default: ''` — пусто, `type: string`). Это ручной путь «or manually» из комментария. Пустой `ref` означает «в каждом целевом репо собирать его дефолтную ветку».
- `repository_dispatch` с `types: [php85-base-ready]` — автоматический путь. Строка типа должна совпадать с той, что отправляет `notify`, точно, с учётом регистра.

Важный нюанс на стыке двух триггеров: контекст `inputs` заполняется только для `workflow_dispatch` (и `workflow_call`). При срабатывании от `repository_dispatch` `${{ inputs.ref }}` вычисляется в пустую строку — обращение к отсутствующему свойству контекста не ошибка, а `null`, который в строке становится `''`. Это удачно совпадает с нужным дефолтом. Практический вывод: **по автоматическому пути `ref` всегда пустой** (все цели собирают дефолтную ветку), потому что `php85-base-ready` пришёл без `client_payload` — базовая сборка физически не может сообщить сюда, какую ветку/SHA брать. Ветку можно задать только руками.

`concurrency:` — сериализация запусков:

- `group: php-8.5-pipeline` — фиксированное имя группы, общее для всех запусков этого workflow.
- `cancel-in-progress: false` — не отменять текущий запуск при поступлении нового; новый встаёт в очередь (`pending`) и ждёт завершения активного. GitHub держит максимум один `running` + один `pending` на группу; если во время ожидания придёт ещё один, самый старый `pending` отменяется.

Почему это здесь критично: пайплайн долгий (он по очереди блокируется на полной сборке каждого целевого репо). Если базовая сборка дважды подряд выстрелит `php85-base-ready`, два перекрывающихся прогона пересборки семейства будут топтать друг друга. `cancel-in-progress: false` гарантирует, что первый доедет до конца, а второй стартует после. `concurrency` объявлен только на верхнем workflow — и это правильное место, потому что весь дерево вложенных workflow с точки зрения GitHub — один прогон, и группа управляет им целиком.

`jobs.pipeline`:

- `uses: ./.github/workflows/rebuild-php.yml` — вызов локального переиспользуемого workflow. Локальный `./`-путь резолвится по SHA вызывающего workflow; так как триггер — `repository_dispatch` (то есть HEAD дефолтной ветки), берётся та же ревизия.
- `with: php: "8.5"` (жёстко зашитая версия), `ref: ${{ inputs.ref }}` (проброс ветки, на авто-пути пустой).
- `secrets: inherit` — передать все секреты вызывающего вниз. Обязательно: ниже понадобится `CI_APP_PRIVATE_KEY` для чеканки App-токена. `vars.CI_APP_ID` наследуется автоматически (переменные, в отличие от секретов, доступны в вызываемых workflow без явной передачи).

## rebuild-php.yml — переиспользуемое ядро

`on: workflow_call` — вызывается только как reusable. Входы: `php` (обязательный, dotted minor вроде `8.5`) и `ref` (необязательный, default `''`).

Смысл, из комментария: для одной минорной версии пересобираются только расширения, попадающие в runtime/dev-образы (apcu, geoip, memcached, redis6, imagick), плюс «хребет» сборки, от которого они зависят по слоям Docker (pear, igbinary, msgpack). igbinary/msgpack сами в образы не ставятся — memcached/redis6 собираются FROM msgpack-базы. Когда все RPM загружены, диспатчится `images.yaml` в самом PHP-репозитории.

Каждая джоба устроена одинаково: `uses: ./.github/workflows/dispatch-and-wait.yml`, `secrets: inherit`, и `with: { repo, ref, php }`. Это и есть тот слой, что запускает `dispatch-and-wait.sh` (чеканит токен под конкретный `repo`, делает `gh workflow run build.yaml -R rpmbsys/<repo> --ref <ref> -f php=8.5` и блокируется на `gh run watch --exit-status`). Порядок задаётся через `needs:`.

Граф зависимостей (`needs`):

```
pear ─┬─► apcu ─► igbinary ─► msgpack ─┬─► memcached ─┐
      │                                └─► redis6 ────┤
      ├─► geoip ────────────────────────────────────►│
      └─► imagick ──────────────────────────────────►│
                                                      └─► images
```

То есть: `pear` — корень; `apcu`, `geoip`, `imagick` стартуют параллельно после pear; хребет `apcu → igbinary → msgpack` строго последователен; `memcached` и `redis6` параллельны после msgpack. Критический путь — шесть уровней в глубину: `pear → apcu → igbinary → msgpack → memcached/redis6 → images`. `geoip` и `imagick` ответвляются рано и идут параллельно всему хребту.

Джоба `images` — особая:

- `needs: [memcached, redis6, geoip, imagick]` — ждёт все *устанавливаемые* расширения.
- `repo: rpmbuild-php-${{ inputs.php }}` → `rpmbuild-php-8.5` (сам PHP-репозиторий, не расширение).
- `workflow: images.yaml` — переопределяет workflow по умолчанию (`build.yaml` у репозиториев расширений).
- Обрати внимание: `php` сюда **не передаётся**. Значит, в `dispatch-and-wait.yml` вход `php` объявлен необязательным (иначе валидация упала бы), и вниз в скрипт уйдёт пустой `PHP` → без `-f php=`. Логично: `images.yaml` в 8.5-репозитории и так привязан к 8.5, фильтр не нужен. Это согласуется с дефолтами скрипта, что мы видели (`WF="${4:-build.yaml}"`, `PHP="${5:-}"`).

## Почему именно такой набор `needs`

Порядок `needs` зеркалит Docker-слои `FROM`: нельзя собрать igbinary, пока нет базы apcu; msgpack — пока нет igbinary; memcached/redis6 — пока нет базы msgpack. geoip/imagick зависят только от pearbuild, поэтому ветвятся сразу.

Тонкий момент, который стоит оценить: `images` перечисляет `[memcached, redis6, geoip, imagick]`, но **не** apcu — хотя apcu тоже устанавливается в образ. Это не упущение: apcu — транзитивная зависимость (`memcached`/`redis6` ← msgpack ← igbinary ← apcu), и `dispatch-and-wait` ждёт полного завершения каждой цели. Значит, к моменту финиша memcached RPM от apcu давно опубликован. То же с igbinary/msgpack — они не устанавливаются, но их завершение гарантировано транзитивно. Так что `needs: [memcached, redis6, geoip, imagick]` — минимально достаточный набор, гарантирующий, что все устанавливаемые RPM на месте. Аккуратно продумано.

И механизм отказоустойчивости: раз `dispatch-and-wait` пробрасывает код возврата цели (через `--exit-status` + `set -e`), падение любого целевого репо роняет соответствующую джобу, а `needs:`-зависимые пропускаются. Сломался, скажем, msgpack → memcached/redis6/images не запустятся, битые образы не соберутся.

## Острые углы

- **Авто-путь всегда собирает дефолтные ветки.** Ни `ref`, ни `client_payload` по `repository_dispatch` не приходят. Ветко-специфичная пересборка — только ручным `workflow_dispatch`.
- **Требование дефолтной ветки — на двух уровнях.** Чтобы `repository_dispatch` вообще сработал, «PHP 8.5 pipeline» должен лежать на дефолтной ветке `rpmbuild-pipeline-php`. Отдельно: чтобы целевой `workflow_dispatch` был диспатчабелен, `build.yaml`/`images.yaml` должны существовать на дефолтной ветке *целевого* репо (даже если `--ref` указывает на другую ветку — тогда возьмётся её версия файла, но сама диспатчабельность определяется по дефолтной).
- **Нет жёсткого таймаута на ожидание.** `gh run watch` ждёт столько, сколько идёт цель; если целевая сборка зависла, джоба висит до дефолтного лимита GitHub (360 мин на job). При длинном критическом пути суммарное время прогона может быть заметным — а `concurrency` ещё и сериализует последующие запуски за ним.
- **Косметика.** В `pipeline` — `ref: ${{ inputs.ref }}` без кавычек, в `rebuild-php.yml` — `"${{ inputs.ref }}"` в кавычках. Оба варианта работают одинаково (выражения вычисляются после парсинга YAML, пустое значение → пустая строка); чисто стилевое расхождение.

Если коротко: верхний workflow — это тонкий вход-ловушка (`repository_dispatch` + ручной запуск + сериализация), вся оркестровка — в `rebuild-php.yml`, где `needs`-граф повторяет слои Docker-образов, а каждый узел — блокирующий кросс-репо диспатч через `dispatch-and-wait`.
